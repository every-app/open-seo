DGTL SEO · Recommended services report

A practical stack for many client websites

Service choices, onboarding and reporting plan · September 19, 2026

Verdict: Keep the existing Cloudflare/TanStack application and Better Auth, and use its Postgres path for a growing shared client platform. Keep Loops for transactional email and the existing Google/DataForSEO connectors. Add a small Clarity summary connector, a proper super-admin workflow, source-aware reports and per-client usage controls.

First action: Build a hosted staging environment and prove two-client isolation before replacing the demo overview with live data.

Clarity API boundary: Microsoft's documented export endpoint is limited to the previous 1–3 days, 10 calls per project per day, three dimensions and 1,000 rows without pagination. Cache a daily snapshot. It exports dashboard insight metrics; heatmaps are viewed or manually downloaded in the Clarity product.

Client onboarding and credential ownership

1. DGTL creates client organization→2. Client admin accepts verified email invitation→3. Add website project→4. Client connects Google and Clarity→5. Jobs refresh separate reports

The current hosted flow permits self-signup and its team invitation function grants admin. For a DGTL-managed service, first enforce invitation eligibility on the server and add a restricted client-reader role; do not rely on hiding the signup button.

  • DGTL credentials: Better Auth secret, Loops key, DataForSEO credential and one Google OAuth application belong to the platform. Store only in Worker secrets or a managed secret store.
  • Client grants: GA4 and Search Console use client consent to Google OAuth. Save encrypted refresh grants and map each allowed property/site to the correct website project. Clarity uses a token generated by a project admin; store it encrypted on the server.
  • Website instrumentation: the client's site must have a GA4 tag and Clarity tracking script, and Search Console must verify ownership. DGTL cannot create historical analytics that were never collected.
  • Client access: project reads and writes require organization membership and a suitable role. Super admins need an explicit platform assignment and audited cross-client actions.

What the super-admin screen must add

  1. Create or suspend a client organization and its first website; invite or revoke the first client administrator. Record the actor and delivery result.
  2. List every client's website, connection state, last successful sync, next run, failed jobs, report freshness and pending invites.
  3. Set client budgets for paid DataForSEO calls, scheduled rankings, crawl size and report frequency. Show current spend and allow an immediate pause.
  4. Assign DGTL analysts to specific clients without granting every staff member global super-admin access.
  5. Keep an audit history for permission changes, connector changes, impersonation/support access, report sharing and client suspension.
