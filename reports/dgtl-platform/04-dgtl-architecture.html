DGTL client portal: architecture, access and data flow

September 18, 2026 · OpenSEO fork · dev-seo · 84e4705

Recommended model: one DGTL platform, a separate organization for each client, and one or more website projects inside each organization. Use seo.dgtl.lk for the portal and keep dgtl.lk as the company website. The hostname and architecture below are proposals, not deployed infrastructure.

High-level system diagram

Authentication proves identity; authorization checks what that identity may do for the selected client and website. Provider secrets remain behind the server boundary.

Client separation and roles

Client A and Client B must be separate organizations. The current project middleware checks a project against the active organization; it does not provide per-client privacy when both clients share that organization.

Proposed roleScopeAllowed actions
DGTL super adminPlatform-wide, explicitly provisionedCreate/suspend clients; assign staff; manage platform settings. Client-data access is explicit and logged.
DGTL analystAssigned client organizationsRun research, inspect analytics, investigate and update problems, create reports.
Client adminTheir organizationManage permitted teammates and website connections; inspect reports.
Client viewerTheir organizationRead dashboards, problems and reports; cannot change connections, users or spend credits.

These are proposed business roles, not a claim that all four exist today. The fork defines owner/admin/member. An organization owner is not a platform super admin, and the existing member can run research, so it is not a strict read-only viewer.

Step-by-step client user flow

Invitation acceptance and email verification are separate checks in the existing implementation. Do not represent an invitation click as verification or grant website access from a link alone. Existing verified users can sign in and accept; new users set a password, verify their email, then accept the invitation.

How data flows

GA4 and Clarity collect events on each client’s website. GSC supplies search data independently; DataForSEO and the crawler supply research and technical findings. DGTL reads authorized results and presents them within the correct client workspace.

  1. DGTL or the client administrator selects the website’s GA4 property, Search Console site and Clarity project.
  2. Server-side connectors retrieve data using the relevant grant or credential. Background jobs carry an explicit organization/project context.
  3. Normalization preserves the source definitions and dates; shared page analysis joins on configured hostname/URL rules, not visitor identity.
  4. The problem service links audit evidence, traffic changes and available behavior signals. Low sample sizes remain visible and suspected causes are labeled as hypotheses.
  5. The browser requests a project view; the server validates session, membership, role and project ownership before returning data.
  6. A report captures a dated view of the findings and recommendations. Report notifications link to the authenticated portal unless DGTL explicitly chooses public sharing.

Existing authentication: useful, but not plug-and-play for DGTL

  • AUTH_MODE=hosted enables the account and team experience; set it for both build and runtime. The current Cloudflare Access path uses a shared workspace and does not fit isolated clients unchanged. Never use local_noauth for this public portal.
  • Email/password signup, email verification with automatic sign-in after verification, password reset, and Google sign-in already exist.
  • Invitations expire after seven days and currently permit only admin. The UI/server invitation function and auth hook must both change to support restricted clients.
  • Signup currently allows public registration and bootstraps workspaces. For an invitation-only DGTL service, enforce eligibility on the server and adapt automatic workspace creation.
  • The app sends transactional emails through Loops. Configure DGTL-owned invitation, verification and password-reset templates and sender-domain records.
  • Hosted billing is connected to Autumn and per-organization credits. Choose whether DGTL pays for all clients or clients pay individually, and adapt these gates deliberately.
  • Use a platform role that is explicitly assigned. An email ending in dgtl.lk must not automatically become a super admin.

Problem reports in a client session

Client opens Overview → selects “Broken internal links” → sees affected pages and crawl evidence → DGTL assigns an analyst → analyst fixes the website → re-crawl verifies the change → report records resolution. For analytics problems, use suitable before/after periods and preserve uncertainty about cause.

The proposed problem record should carry a stable ID, client/project IDs, source evidence, affected URLs, severity, impact estimate, status, assignee, first/last detected dates and verification history. Keep issue state separate from the immutable report that describes it.
