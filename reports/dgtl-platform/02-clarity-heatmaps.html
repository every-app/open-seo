Clarity heatmaps and the DGTL integration boundary

September 18, 2026 · OpenSEO fork · dev-seo · 84e4705

Verdict: integrate Clarity summary metrics first, and link to its heatmaps. The documented Data Export API does not provide a full heatmap/replay rendering interface. An API token alone cannot deliver an embedded clone of the Clarity experience.

What the public integration supports

Project admins generate a token in Settings → Data Export. The bearer-token endpoint returns dashboard summaries such as traffic, engagement, scroll depth and frustration metrics, with breakdowns including URL and device. Documented limits are 10 requests per project per day, the previous 1–3 days, three dimensions per request, and 1,000 rows without pagination. These limits apply to the export API, not the full Clarity interface. Microsoft Data Export API.

The published endpoint does not document page screenshots, element coordinates, DOM snapshots, or recording payloads. Therefore, full heatmaps inside DGTL are a separate implementation or supported-provider capability to validate; do not promise an iframe or automatic Clarity single sign-on.

Recommended integration design

  1. Install the correct Clarity project tag on each client’s website, using the website’s consent and masking settings. A tag on DGTL’s portal would measure the portal, not the client’s site.
  2. Bind the client organization and website to its Clarity project and encrypted API token. Verify the association during onboarding.
  3. Fetch summaries in a scheduled server job, within the daily quota. Cache results so dashboard visits do not consume calls.
  4. Show supported behavior metrics in DGTL and add “Open heatmap in Clarity.” The client needs Clarity project access and may need a separate sign-in.
  5. Store fetch time, actual rolling-window boundaries, dimensions, row-limit warnings and connection status. A 30-day history must accumulate after setup; the API cannot simply backfill 30 days.

Do not sum overlapping rolling windows or unique-user counts into a monthly total. Preserve source windows and define each aggregation explicitly; missed export windows and truncated results must remain visible.

If heatmaps must stay entirely inside DGTL

Choose this as an explicit second project: evaluate a provider with a supported embedded viewer, or build a recording/heatmap collection pipeline. That requires client-site collection, stable element identification, page-state capture, responsive layout handling, masking, storage, aggregation and a renderer. The current fork contains none of that pipeline.
