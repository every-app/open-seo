GA4 connection and analytics in the existing repository

September 18, 2026 · OpenSEO fork · dev-seo · 84e4705

Yes, GA4 can connect to your existing repository, and the connector already exists. Use a Google OAuth client ID and secret, then let an authorized account select the client’s GA4 property. A generic API key or a website measurement ID is not sufficient to read private analytics.

What exists today

  • A Connect with Google flow, GA4 property picker and disconnect controls.
  • A project-to-property mapping and encrypted OAuth access/refresh tokens.
  • An organic traffic dashboard card with a 28-day trend and previous-period comparisons.
  • Reporting services and MCP tools for detailed analytics, including measurement health and combined GSC/GA4 opportunities.

Code evidence: connection UI, OAuth and encryption configuration, GA4 tool definitions. The report backend is broader than the current browser UI.

Connection setup, step by step

  1. Create or choose a DGTL Google Cloud project. Enable Google Analytics Admin API for property discovery and Data API for reports; enable Search Console API if using GSC.
  2. Configure the OAuth consent screen for the DGTL app. For external client accounts, use an appropriate external app configuration and complete Google’s production verification requirements as applicable.
  3. Create Web application OAuth credentials. Register exact callback URLs for the deployment mode and pinned Better Auth version.
  4. Set the client ID, secret and auth encryption secret on the server. For the client portal, configure hosted auth at both build time and runtime, with the chosen HTTPS portal origin.
  5. Ensure the client website already sends GA4 events. Connecting an account does not install the website tag or create historical data.
  6. In project settings, choose Connect with Google, approve the read-only Analytics scope, and select the correct property. Check hostname, timezone and currency.
  7. Verify a known period against GA4, test revoked access and reconnection, then expose the additional report services in the portal UI.

Google requires authorized user or service-account access to read properties: Analytics API quickstart. This repository uses user OAuth with analytics.readonly and offline refresh, not a service-account upload workflow. Google web-server OAuth guide.

The latest Better Auth documentation changes callback behavior compared with its 1.6 line. Follow the repository’s pinned version and the actual outgoing redirect URI; upgrading auth is a separate change. See the versioned 1.6 guide and repository GA4 setup guide.

Authentication, consent and client data

Signing in to DGTL proves who the user is. Granting GA4 access separately authorizes the application to read a property. Neither action by itself grants access to another client’s project.

Bind every selected property to the authorized client/project. Keep tokens server-side, scope caches by client and project, and let permitted users reconnect or disconnect. The repository allows a Google connector account to differ from the portal email, which suits agency-managed properties.

GSC clicks, GA4 sessions and Clarity page views use different definitions and coverage. Present them side by side with source labels; do not add them together or promise exact matching.
