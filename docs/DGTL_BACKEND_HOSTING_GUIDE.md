# DGTL SEO backend and hosting guide

This guide explains the recommended backend in plain language. It is written
for the DGTL SEO client portal, where DGTL staff manage several client
organizations and every client can see only their own websites and reports.

## Recommendation

Use this production stack:

| Need | Recommended service | Why |
| --- | --- | --- |
| Web application and backend | Cloudflare Workers | The repository is already built for Workers and uses Cloudflare bindings. |
| Main database | Managed PostgreSQL through Cloudflare Hyperdrive | Suitable for a growing shared application and already supported by the code. |
| Authentication | Existing Better Auth hosted mode | Email/password, verification, sessions, invitations and organization roles are already implemented. |
| Transactional email | Existing Loops integration | Verification, password reset and invitation emails are already implemented. |
| SEO data | DataForSEO | The existing keyword, domain, backlink and rank-tracking code uses it. |
| Search performance | Google Search Console OAuth | Gives actual Google clicks, impressions, queries and positions. |
| Web analytics | GA4 OAuth and Data API | Gives traffic, landing pages, engagement and conversions. |
| Behavior analytics | Microsoft Clarity | Use its tracking script and export summaries; link users to native heatmaps. |
| Files and report artifacts | Cloudflare R2 | The repository already declares an R2 binding. |
| Scheduled work | Cloudflare Cron and Workflows | The current audit and rank-tracking jobs already use them. |
| Secrets | Cloudflare Worker secrets | API keys and tokens stay encrypted and server-side. |
| Monitoring | Cloudflare logs plus PostHog | Track failures, connector health and product activity. |

For the first staging deployment, D1 is acceptable. Before onboarding many
paying clients, load-test D1 against the expected number of websites and jobs.
Move to the repository's PostgreSQL path when the shared database workload,
report history or operational requirements justify it.

## Why Cloudflare fits this repository

This code is not an ordinary Node container application. It uses:

- Cloudflare Workers for server requests.
- D1 or PostgreSQL through Hyperdrive for relational data.
- R2 for object storage.
- KV for small key-value state.
- Durable Objects for agent chat state.
- Workflows for audits and rank checks.
- Cron triggers for scheduled jobs.

Deploying the container to AWS App Runner or DigitalOcean App Platform would
run the web process, but it would not automatically replace these bindings.
DGTL would have to redesign D1, R2, KV, Durable Objects, Workflows and Cron with
the chosen provider's equivalents.

## What the backend does

The normal request flow is:

```text
Client browser
    -> DGTL SEO route
    -> Better Auth session check
    -> organization membership and role check
    -> project ownership check
    -> validated server function
    -> business service
    -> repository query or provider API
    -> normalized result or saved snapshot
    -> client dashboard/report
```

The browser must never call DataForSEO, Loops or Clarity with a secret. It calls
a DGTL server function. The server verifies the user and project first, then
uses the server-side credential.

## Multi-client data model

Use these boundaries consistently:

```text
DGTL platform
  -> client organization
       -> organization members and invitations
       -> website project A
            -> GA4 property
            -> Search Console site
            -> Clarity project
            -> audits, rankings and reports
       -> website project B
            -> its own connections and reports
```

Every table and background job must carry an organization ID or an authorized
project ID. The server must apply that condition to every read and write.

## Authentication and email process

1. A DGTL super admin creates a client organization and its first website.
2. DGTL sends an invitation to the client's administrator.
3. Loops sends the DGTL-branded email from a verified DGTL sending domain.
4. The recipient opens the link, creates or signs into an account, and verifies
   the email address.
5. Better Auth creates the organization membership and session.
6. The user can open only projects belonging to that organization.
7. Password-reset and verification messages also go through Loops.

The current local demo account is not production authentication. Production
must use `AUTH_MODE=hosted`, a strong `BETTER_AUTH_SECRET`, HTTPS, verified
email delivery and server-enforced invitations.

Loops is for messages generated by the application. Use a DGTL Google Workspace
or Microsoft 365 shared mailbox for human support conversations. Those are two
different services.

## Super-admin responsibilities

The super-admin area should eventually support:

- Create, suspend and reactivate a client organization.
- Create website projects and invite or revoke client users.
- Assign DGTL staff to specific clients.
- See GA4, Search Console, Clarity and DataForSEO connection health.
- See the last successful refresh, next scheduled run and failed jobs.
- Set paid API budgets, crawl limits and ranking schedules per client.
- Pause a client's paid background work immediately.
- Review an audit history of access, invitations and connector changes.
- View client reports for support with a recorded reason.

An email-domain check is not enough for super-admin access. Keep an explicit
platform-admin assignment and record every cross-client action.

## Separate data sources in reports

Do not merge every metric into one unexplained score.

| Report | Source | What it means |
| --- | --- | --- |
| SEO research | DataForSEO | Third-party keyword, domain and backlink estimates. |
| Search performance | Search Console | Actual Google search clicks, impressions and positions. |
| Web analytics | GA4 | Sessions, engagement, landing pages and key events. |
| Technical SEO | Site audit workflow | Crawl problems tied to affected URLs and an audit date. |
| Behavior | Clarity | Recent engagement, scroll and frustration summaries. |
| DGTL problem report | Joined evidence plus analyst review | A tracked issue with source links, owner, status and verification. |

Every displayed number should name its provider, property/site, date range,
timezone and last refresh time.

## Hosting comparison

### Cloudflare: recommended

Use the existing native deployment. It requires the least code change and
keeps the audit, rank, storage and scheduled-work architecture intact. Add a
managed PostgreSQL origin through Hyperdrive when required.

### AWS: powerful, but a migration

An AWS version would normally use App Runner or ECS, RDS PostgreSQL, S3, SQS,
EventBridge Scheduler and Secrets Manager. AWS gives broad enterprise controls,
but DGTL would need to replace the Cloudflare-specific bindings and workflows.
Choose AWS when the company already has AWS skills, compliance requirements or
other systems there and has budget for the migration and ongoing operations.

### DigitalOcean: simple containers, but still a migration

App Platform and Managed PostgreSQL are easier to learn than a full AWS stack.
They can run a normal Docker application, but the current Docker mode disables
application authentication and does not provide the same Workflows, Durable
Objects or D1 setup. Use DigitalOcean only after creating a production Docker
architecture with hosted auth and replacements for Cloudflare services.

## Docker: local learning path

The supplied Docker setup is for local or private testing. It forces
`AUTH_MODE=local_noauth`, so do not expose it directly to clients.

After Docker Desktop is healthy:

```sh
cp .env.example .env
```

Set the DataForSEO credential in `.env`, then build the DGTL code:

```sh
docker build -f Dockerfile.selfhost -t dgtl-seo-tool:local .
```

Run it through the existing Compose file:

```sh
OPEN_SEO_IMAGE=dgtl-seo-tool:local docker compose up -d
docker compose ps
docker compose logs -f open-seo
```

Open `http://127.0.0.1:3001`. Check health with:

```sh
curl http://127.0.0.1:3001/api/health
```

Stop the container with:

```sh
docker compose down
```

The Compose volume `open_seo_data` keeps the local D1/KV/R2 emulator state.
Removing that volume deletes the local Docker data.

## Production rollout order

1. Create a DGTL staging Cloudflare account/environment and staging hostname.
2. Configure hosted auth, Loops, Google OAuth and DataForSEO as encrypted
   secrets.
3. Apply database migrations and create two internal test organizations.
4. Verify that neither test client can read the other client's projects,
   reports, caches or job results.
5. Connect one test website to Search Console, GA4 and Clarity.
6. Replace dashboard demo values one source at a time.
7. Add budgets, connection health, audit history and staff assignments to the
   super-admin area.
8. Run backup/restore, expired-token, failed-email and API-rate-limit tests.
9. Invite the first real client only after those checks pass.

## Learning order

Learn the system in this sequence:

1. HTTP request and response basics.
2. Environment variables and secrets.
3. Relational database basics: tables, primary keys, foreign keys and joins.
4. Sessions, authentication, authorization and organization roles.
5. OAuth consent and refresh tokens.
6. Background jobs, retries and idempotency.
7. Logs, health checks, backups and incident recovery.
8. Docker images, containers, ports and persistent volumes.
9. Cloud deployment, DNS and HTTPS.

Do not start by learning every AWS or Cloudflare product. Follow one request
through this repository, then connect one provider and inspect the stored rows
and logs. Repeat that process for each feature.
